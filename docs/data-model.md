# Data Model

This document describes the first Cloudflare D1 CRM persistence layer. The schema is normalized, deterministic, and designed for Phase 1 mock/demo data without Money S4 assumptions.

## Internal IDs And External IDs

Application tables use stable text IDs generated by the application or seed process.

ERP-facing records store external IDs separately:

- `customers.external_id`
- `customer_locations.external_id`
- `products.external_id`
- `orders.external_id`
- `order_items.external_product_id`

External IDs are nullable because not every CRM record must originate from an ERP. When present on primary ERP-imported entities, they are unique so future idempotent synchronization can upsert safely.

## Migration Policy

`0001_initial.sql` is the accepted pre-production baseline migration.

After the database foundation checkpoint, `0001_initial.sql` must be treated as immutable. All future database schema changes must use sequential migrations such as `0002_...`, `0003_...`, and so on. Do not modify old applied migrations after this baseline checkpoint.

## Core Entities

- `users`: internal users and roles. Supports admin, manager, customer service, and sales representative records without implementing login.
- `customers`: normalized customer identity, assignment, B2B status, active flag, source, and optional `metadata_json` for future extensibility.
- `customer_locations`: multiple POS, warehouse, billing, delivery, headquarters, or other locations per customer.
- `products`: normalized product references needed for order history and future cross-sell analysis.
- `orders`: customer order headers with status, source, dates, and amounts.
- `order_items`: historical order lines. Product name, SKU, and external product ID are copied onto each line so history remains understandable if product records later change.

## Customer Metadata JSON Rule

`customers.metadata_json` is only for optional non-core extension data.

Do not store fields in metadata JSON when they are required for filtering, sorting, segmentation, KPI calculations, reporting, joins, permissions, or frequent querying. Such data must use proper schema fields or normalized tables.

## Operational CRM Entities

- `customer_interactions`: broad interaction model for calls, email, notes, meetings, customer service events, and other activity.
- `sales_visits`: structured sales representative visit planning and completion records. A visit may link to the Sales task that initiated it and stores controlled result, next-action, follow-up, and idempotency values.
- `tasks`: assigned work items with due dates, priority, status, type, and optional links to customers, locations, source interactions, and source visits. These normalized links support Customer Service to Sales handoff and the reverse without parsing notes.

## Campaigns

- `campaigns`: campaign metadata and lifecycle.
- `customer_campaigns`: customer membership and activity events for send, open, click, conversion, and optional conversion order. `UNIQUE (campaign_id, customer_id)` prevents duplicate membership in the same campaign.

## Segments

- `customer_segments`: configurable segment definitions. Phase 1 seeds the approved system segments:
  - `ACTIVE`
  - `REORDER_DUE`
  - `DECLINING`
  - `AT_RISK`
  - `CRITICAL`
  - `REACTIVATION`
  - `B2B_MISSING`
  - `CROSS_SELL`
  - `NEWSLETTER_FOLLOW_UP`
- `customer_segment_memberships`: many-to-many customer segment assignment with reason, score, assigned date, optional expiry, and update timestamp.

Automatic segment calculation is intentionally not implemented yet.

## Derived Metrics

`customer_metrics` stores the current calculated metrics row per customer:

- order dates
- rolling turnover windows
- previous period comparison
- average order value
- average reorder days
- days since last order
- rolling and lifetime order counts
- lifetime turnover

These values are deterministic application data. They must not depend exclusively on generative AI. A future metrics engine can calculate and refresh them.

## KPI Foundation

- `kpi_definitions`: data-driven KPI definitions such as calls completed, visits completed, and turnover.
- `kpi_targets`: targets by user or role over a time period with optional weighting.

Payroll and bonus calculations are intentionally not implemented.

## Configuration

`system_config` provides a lightweight typed key/value mechanism for future configurable business rules, including reorder grace days, at-risk days, critical inactivity days, and reactivation days. `system.business_timezone` is the IANA timezone used to convert business dates into UTC query boundaries; timestamps remain stored in UTC.

## Synchronization Metadata

`sync_runs` records future provider/entity synchronization attempts:

- provider
- entity type
- start/finish time
- status
- imported/updated/skipped/failed counts
- cursor/checkpoint
- error message

No ERP connection exists in Phase 1. The table prepares for future incremental, idempotent synchronization.

## Important Relationships

- Customers may have many locations, orders, interactions, tasks, visits, campaign memberships, and segment memberships.
- Orders have many order items.
- Customer locations belong to customers and may be referenced by orders, interactions, tasks, and visits.
- Tasks reference assigned users and may reference creator users and source interactions.
- Sales visits reference sales representative users.
- Campaign memberships may reference a conversion order.

## Indexes

The first migration creates indexes for common CRM reads:

- users by role/active
- customers by company name, active status, assigned sales representative, and B2B status
- customer locations by customer/active
- products by category/active
- orders by customer/date and date
- order items by order and product
- interactions by customer/date and user/date
- visits by customer/planned date and sales rep/status
- tasks by assigned user/status/due date and customer/status
- campaign memberships by customer
- segment memberships by segment
- sync runs by provider/entity/start time

## Future Extension Points

- Add metrics refresh services inside `packages/db` or a dedicated domain package before exposing metrics-heavy dashboards.
- Add segment rule configuration and deterministic segment calculation before adding AI recommendations.
- Add auth tables or identity mapping when authentication is explicitly requested.
- Add concrete ERP provider synchronization only in Phase 2 with the client's IT department.
- Consider queues/workflows only when import or calculation jobs become long-running.
